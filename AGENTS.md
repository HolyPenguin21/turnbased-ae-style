# Инструкции для работы с проектом

## Контекст и источники
- Unity/C# проект пошаговой стратегической игры.
- Репозиторий: HolyPenguin21/turnbased-ae-style. Основная ветка: master.
- Версию Unity определять по ProjectSettings/ProjectVersion.txt; зависимости — по Packages/manifest.json и lock-файлу.
- Перед анализом и изменениями читать актуальные файлы целевой ветки. Код — источник истины; история чатов и документы описывают контекст, но могут устаревать.
- Общаться с владельцем на русском.

## Изменения
- Сначала проследить цепочку вызовов и причину проблемы; затем внести минимальное достаточное исправление.
- Использовать существующие классы и методы; перед добавлением логики проверить, нет ли аналогичной реализации.
- Не выполнять посторонний рефакторинг, обновление пакетов или изменение игрового баланса без связи с задачей.
- Для AI проверять влияние на распределение ресурсов, резервы, владение миссиями, жизненный цикл исполнителей и повторную оценку в течение хода, если задача затрагивает эти области.
- Не переносить временные решения или заглушки проверочной среды в игровой код.
- Сохранять Unity .meta, GUID и сериализованные ссылки. При перемещении ассета перемещать его .meta вместе с ним.
- Сцены, префабы, ассеты и настройки изменять только в рамках задачи.
- Соблюдать .gitattributes; избегать массовых изменений форматирования.
- В репозитории существуют Docs/ и docs/. Использовать точный регистр существующего пути; не объединять и не переименовывать папки без отдельной задачи.

## Проверки
- Выбирать проверки по области изменений. Для исправления поведения использовать подходящий существующий тест или добавить проверку исходного сбоя.
- Для AI сначала прочитать Tools/ai-verify/README.md. В среде без Unity сохранить compile baseline до изменений и сравнивать тесты с исходной ревизией задачи.
- Инструменты ai-verify используют старые Unity reference DLL и заглушки; успешная проверка не доказывает успешную сборку в текущем Unity.
- Не обновлять baseline после исправления, чтобы скрыть новые ошибки.
- После ручного изменения Unity YAML запускать оба инструмента из Tools/unity-yaml-verify/README.md для изменённых файлов.
- Для окончательной проверки в редакторе использовать Unity версии проекта и полный набор EditMode тестов; дополнительно проверить затронутый игровой сценарий.
- Если Unity или другая проверка недоступны, прямо сообщить, что не запускалось. Не заявлять об успешной компиляции, тестах или запуске без результата проверки.
- Для изменений только документации сверять пути, команды и версии с репозиторием; игровые тесты не требуются.

## Git и отчёт
- Перед записью через коннектор читать актуальное содержимое файла и его SHA. Не перезаписывать чужие изменения.
- Коммиты, push и merge выполнять, когда это указано или однозначно разрешено в задаче. Целевую ветку брать из задачи; по умолчанию основной веткой считать master.
- Отчёт: что изменено и зачем, затронутые файлы, влияние на поведение, выполненные проверки и оставшиеся проверки в Unity.
- Для изменений кода указывать масштаб: локальное исправление, изменение поведения или изменение архитектуры.
