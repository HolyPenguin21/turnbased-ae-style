# Повторная проверка производительности снизу вверх — 18.11.2026

Проверено рабочее дерево `audit/cache-consistency` с исправлениями кешей от
17.11, относительно базы `ab66ad13a644c0503d76a40336f3eea87dface41`.
В этой перепроверке игровой код не изменялся. Расширены только диагностический
инструмент и отчёт. SHA-256 совокупности путей/содержимого 724 runtime C# файлов:
`ac9412d720d005045de553b24bdafcc10b42483a463fecb51610cf704d77ab69`.

## Вывод

Прошлая оценка была неполной: дешёвый lookup не означает дешёвый путь его вызова.
Подтверждены существенные расходы до lookup и плохое поведение при переполнении.
Показанные ранее 40 B относятся к низкоуровневому ScarcityProfile без живого
callback, а не к полной карточной оценке. Ускорения 73×/25× относились к конкретному
одному defending army и не характеризовали бой с несколькими армиями.

Наиболее полезные следующие изменения: устранить повторные расчёты свободных
ресурсов в одной оценке; убрать ненужные коллекции из чтения книги ресурсов;
заменить полную очистку scarcity memo ограниченным вытеснением. Следом — расходы
на строковые ключи и подготовку боевых входов. Эти оптимизации данным аудитом
не реализованы, чтобы измерения и исправления оставались различимы.

## 1. От чтения ресурса к карточному потребителю

Фактический путь:
`StrategicResourceCostValue` → `ActionPrice.Resources` → `ScarcityProfile` →
`StrategicSpendability.SpendableAmount` → `TurnResourceBook.Free`.
Тот же callback также вызывается до Resources при расчёте residual preservation.

`TurnResourceBook.Free` каждый раз создаёт claims-список; `Outstanding` каждый раз
создаёт owner dictionary, в том числе при пустых claims и отсутствии drawsByOwner.
Это происходит до проверки наличия нужного профиля цены в кеше.

Карточный сценарий использует цену с четырьмя положительными компонентами,
64 карты колоды, отсутствие starvation evidence и 0/16/64 резервных строк.
Все резервы — реальные записи StrategicResourceReservationLedger, разнесённые
по четырём физическим ресурсам. Root, ledger, authority-проверки и callback —
настоящие реализации проекта, не имитация математической формулы.

| Прогретый путь | мкс/вызов | Managed B/вызов |
| --- | ---: | ---: |
| ScarcityProfile, snapshot stockpile, 64 карты | 0.373 | 40 |
| ScarcityProfile + live spendable, 0 строк резервов | 0.623 | 584 |
| ScarcityProfile + live spendable, 16 строк | 2.098 | 2984 |
| ScarcityProfile + live spendable, 64 строки | 5.286 | 7592 |
| StrategicResourceCostValue, 0 строк | 0.878 | 1216 |
| StrategicResourceCostValue, 16 строк | 3.797 | 6016 |
| StrategicResourceCostValue, 64 строки | 13.856 | 15232 |

Отдельный dry-run подтвердил **4 callback-чтения** на один ScarcityProfile и
**8** на одну четырёхресурсную карточную оценку. Счётчики не стояли в timed callback.
При пустой книге переход от raw 40 B к 584 B даёт дополнительные 544 B на четыре
resource-запроса. Полный caller повторяет их дважды и оплачивает lambda-wrapper.

Даже без live callback `ActionPrice.Resources(ResourceCost, ...)` выделяет
**128 B** против 40 B у самого профиля: захватывающая lambda в overload добавляет
88 B. Это отдельная цена обёртки, а не словаря кеша.

Проверена также живая форма списков: 16 hand + 64 deck. Одно прогретое чтение
выполняет один Count и 16 индексных чтений руки, один Count и 64 индексных чтения
колоды. Проверка фактов O(hand+deck), а не O(1), даже при cache hit. В этом сценарии
новая версия выделяет 40 B против 200 B в базе; первый аудит измерял другую форму
входа — пустую руку и массив колоды.

Безопасные направления исправления:

- Получать четыре spendable-значения один раз на синхронную карточную оценку и
  использовать их для preservation и ActionPrice. Нельзя сохранять их на весь ход
  без протокола invalidation: резервы меняются в течение хода.
- Разделить быстрый случай Outstanding без drawsByOwner и общий случай
  с вычетом по владельцу. Сохранить MayDrawOn, deferred income credit, owner authority
  и граничные float-проверки; не заменять их чтением только stockpile.
- Не объявлять весь путь allocation-free после устранения одного float[4].

## 2. От capacity одного memo к потере повторного использования

`ActionPrice` хранит до 64 профилей на snapshot и делает `Profiles.Clear()` при
промахе на заполненном кеше. Dry-run читает настоящую memo-таблицу; reflection
выполняется вне timed-прохода и не меняет стратегию вытеснения.

| Последовательность, 1024 запроса | Hits | Misses | Полных очисток |
| --- | ---: | ---: | ---: |
| Цикл из 64 различных supply | 960 | 64 | 0 |
| Цикл из 65 supply | 0 | 1024 | 15 |
| 63 горячих supply + новый каждый 64-й запрос | 63 | 961 | 15 |

65 ключей при 64 слотах сами по себе не доказывают неудачную политику: такой цикл
может вытеснять данные даже при LRU. Существеннее последний случай: горячие 63
ключа помещаются, редкий новый ключ составляет всего 1/64 запросов, но полная
очистка снова уничтожает всю горячую часть. При сохранении этой части можно было бы
получить 945 hits на данной последовательности; текущая реализация даёт только 63.

Timed-проход с заранее прогретыми 63 ключами:

| Нагрузка | мкс/вызов | B/вызов |
| --- | ---: | ---: |
| Только горячие 63 | 0.332 | 40 |
| Те же 63 + редкий новый каждые 64 вызова | 5.167 | 11064.6 |

Получилось примерно **16×** по времени и **277×** по managed allocations в этом
синтетическом сценарии. Поведение воспроизведено и на ab66ad1: это существующая
политика, а не регрессия последнего исправления точности ключа. Реальная частота
такого паттерна в матче пока не измерена. Увеличение лимита только отодвинет порог;
нужно ограниченное вытеснение с сохранением горячих записей и отдельной проверкой
стоимости bookkeeping на попадании.

## 3. От числового ключа авиации к словарю

Для того же 3v2 измерены настоящие BuildKey и KeyString. Delegate к private
KeyString и доступ к cache dictionary подготовлены до таймера.

| Слой | мкс/вызов | B/вызов |
| --- | ---: | ---: |
| BuildKey | 0.418 | 1648 |
| KeyString для готового int[] | 0.878 | 776 |
| TryGetValue с заранее готовой строкой | 0.093 | 0 |

Итого два подготовительных слоя дают **2424 B**, почти всю ранее измеренную
цену публичного авиационного hit (**2456 B**). Корень расходов — List/int[] и
`string.Join`, а не Dictionary.TryGetValue. На miss KeyString вызывается при
lookup и при Store повторно. Микросерии CPU нельзя механически складывать:
у них отдельные окна и разное GC-состояние; allocations здесь дают более устойчивую
декомпозицию.

Замена строкового ключа должна сохранять полное равенство последовательности,
отдельные partition/fate/consumption/collateral inputs и прежний seed. Один hash
без проверки полного равенства вернул бы ошибки корректности.

## 4. От одиночного боя к нескольким defending armies

Прежний public EstimateSequential с одним defending army переходил в обычный
Estimate. Добавлен настоящий случай с двумя армиями по два защитника.

| Путь | мкс/вызов | B/вызов |
| --- | ---: | ---: |
| WorthIt, две армии, warm, ScopeTiming off | 6.375 | 11896 |
| Тот же путь, ScopeTiming on | 6.708 | 11896 |
| Тот же путь без верхнего estimate cache | 475.004 | 57592 |
| Aviation AgainstArmies, две армии, warm | 2.749 | 4952 |
| Тот же aviation путь без верхнего кеша | 55.911 | 96304 |

Кеши сохраняют большую пользу: около 75× и 20× именно в этих входах. Но ground
hit — уже почти **12 КБ**, а не прежние 3832 B. Public wrapper до lookup заново
собирает summons/armies, ранжирует оборону, преобразует rosters и строит templates.
При 3000 внешних запросах последнего окна: **9001 hits, 2 misses, 2 entries** —
ранжирование и итоговый sequential estimate обращаются к кешу несколько раз.
Hits нельзя приравнивать к числу решений или армий.

Рост одиночного состава с 3v3 до 12v12 поднял warm allocations с **3832** до
**10168 B**. Хранить результат расчёта правильно; следующий резерв — подготовка
неизменных входов и конструирование ключа. Без проверки текущих wounds, summons,
weather и consumption переносить кеш выше этой подготовки нельзя.

## 5. От дешёвого delta lookup к построению Development scope

Ранее 0 B относились только к EquipmentDelta.GetOrCompute с готовыми ScopeKeys,
recipient stamp и простым вычислителем. Добавлена стоимость настоящих
RecipientVerdictKey и RecipientDeltaCoreKey.

Сценарий: 64 карты колоды, 0 либо 6 snapshot-армий по 12 одинаковых профилей.
Live recipients, sightings, facilities и active missions не зарегистрированы;
это неполная игровая ситуация и не замер всей Development enumeration.

| Ключ | Армий | мкс/построение | B/построение | Символов в результате |
| --- | ---: | ---: | ---: | ---: |
| Full verdict | 0 | 11.768 | 40240 | 7659 |
| Core delta | 0 | 3.710 | 16740.9 | 7226 |
| Full verdict | 6 | 19.606 | 87648 | 13298 |
| Core delta | 6 | 11.948 | 77911.5 | 17257 |

Это измеримый расход: даже с прогретыми вспомогательными row/benchmark memo
собираются списки, сортировки, joins и большие итоговые строки. Но он **не
оплачивается на каждый equipment delta hit**. RecipientVerdictKey строится в
точках перечисления возможностей; StoreWithDeltaScope создаёт core key один раз
для нового verdict store. Приоритет оптимизации зависит от частоты смены store
в настоящем ходу; умножать эти числа на каждую пару equipment×recipient неверно.

Нужно сохранять владельца фактов и точные зависимости ключа. Простая подмена
содержания счётчиком размера списка повторит исправленную проблему ActionPrice.

## 6. От cost-only маршрута к witness, диагностике и завершению матча

Hit и miss теперь используют один и тот же путь 24 шага. Для miss очищается
только существующий routes-словарь; Clear входит в интервал. Grid, map и память
остаются прогретыми. Reflection для доступа к словарю выполняется при подготовке.

| Вызов | мкс | B/вызов |
| --- | ---: | ---: |
| Cost-only hit, ScopeTiming off | 0.050 | 0 |
| Cost-only hit, ScopeTiming on | 0.110 | 0 |
| Witness hit | 0.073 | 288 |
| Тот же маршрут, miss + Clear | 5.615 | 736 |

288 B — намеренная защитная копия пути. Убирать её ради zero-allocation нельзя.
ScopeTiming в реальном AiTurnController включается вместе с AiTurnFrameStats;
предыдущий выключенный замер был нижней границей. Абсолютная добавка мала, но
на очень дешёвом lookup сбор диагностик дороже части самого lookup.

Отдельный контроль делегата/записи — около 0.001 мкс, warm GridFor — 0.003 мкс.
Это наносекундный режим в .NET JIT, близкий к стоимости измерительной петли.
Из него нельзя выводить точную native Unity цену или коэффициент ускорения тысячи раз.

После заполнения 128 маршрутов вызван настоящий MatchStateInventory.EndMatch:
**128 маршрутов остались**, в статическом словаре остался 1 player cache, а
`_cacheMap` всё ещё ссылается на прежнюю карту. Inventory классифицирует эти кеши
как versioned и не назначает им reset callback. Следующее подходящее обращение
проверяет identity/version и безопасно инвалидирует данные.

Это доказанное удержание последнего managed-набора после reset, а не доказанная
накопительная утечка или размер native/GPU-памяти. Нужен lifecycle-замер в меню
в Unity; возможное исправление — явный сброс владельцем cache-state на выходе,
с проверкой незавершённых поисков и арендуемых buffers.

## Метод и воспроизводимость

31 сценарий, 7 отдельных окон, два runtime (ab66ad1 и рабочее дерево).
Оба законченных запуска прошли: по 1 диагностической NUnit fixture, без ошибок.
Это не повторный полный EditMode-прогон.

- [Медианы всех сценариев](Cache_BottomUp_Performance_2026-11-18.csv).
- [Все 434 окна с Gen0-счётчиками](Cache_BottomUp_Windows_2026-11-18.csv).
- [Команды и точные границы адаптеров](../Tools/cache-verify/README.md).

Запуски выполнялись последовательно, с .NET 8.0.428 SDK / 8.0.34 runtime,
оптимизациями и выключенным tiered JIT. Подготовка snapshot, root, delegates,
первичное заполнение и reflection не входят в timed lookup. Отдельные dry-runs
считают чтения/callbacks и inspect настоящие cache entries. Остальные native
reference-адаптеры те же, что в предыдущей проверке; в Assets они не записываются.

Все ключевые проблемы воспроизводятся и на базе: обе версии дают одинаковые
capacity/lifetime-счётчики и одинаковые allocations неизменённых слоёв.
Поправка ActionPrice уменьшает allocations профиля, но не устраняет расходы его
потребителей. Небольшие межпроцессные CPU-различия не приписываются изменениям
исходников; приоритет выводится из кода, стабильных байт и счётчиков, а не из
разницы нескольких наносекунд. Большие allocations вызывают Gen0 во время окон;
их влияние не вычиталось. Число сборок в .NET runner не прогнозирует Unity GC-паузы.

Камера/Input System hover, native lifetime, настоящий длинный ход, editor asset
loading, дисковый I/O и целевая Mono/IL2CPP-платформа не измерены. Для hover уже
есть Explicit native cached/direct probe. Остальные кеш-семейства из предыдущего
аудита не получили новых throughput-замеров в этом углублённом проходе.

## Порядок следующих исправлений

1. Локальное повторное использование четырёх spendable значений и быстрые чтения
   TurnResourceBook без лишних коллекций; сохранить authority и deferred-credit правила.
2. Ограниченное вытеснение scarcity-профилей; отдельно проверить 64/65 циклы,
   горячие 63 + редкие новые, корректность float keys и стоимость попадания.
3. Numeric sequence key авиации с полным equality и прежним seed; затем повторная
   подготовка multi-army rosters и Development scope keys по реальному профилю хода.
4. Явный lifecycle cache cleanup, если Unity Memory Profiler подтвердит значимый
   удержанный объём; проверить выход и restore при незавершённых операциях.
