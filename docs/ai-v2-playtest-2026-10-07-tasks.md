## T1. Скауты повторяют `MoverContended` и `NoMoverExists`

**Наблюдение.**
- В логе 596 строк `[Loop] assignment-batch … FAIL`: 391 `MoverContended`, 143 `NoExecutableStep`, 62 `NoMoverExists`. Все с диспозицией `RetryNextTurn`.
- В `[Lifecycle]` это 423 результата `Waiting` с `prov=MoverContended`.
- Одни и те же цели `Explore` повторяются 33–52 раза за запуск: `Explore 5,1` (52), `-6,4` (50), `5,-2` (48), `-4,-1` (37), `3,0` (33). Примеры: строка 143 («a capable solo Recce exists but is spent / activated / claimed this cycle»), строка 333 («no solo Recce on the map»).
- Операции не выполняются и не закрываются, а пересчитываются каждый цикл. Часть интентов `Explore` потом закрывается по простою (`reaped … stall 2/2, age 13/6`, строка 25557).

**Что выяснить.**
1. Это повторные попытки в пределах одного хода (лишняя работа) или несколько ходов подряд без мувера? Построить таблицу по ходам и игрокам для одной цели.
2. Действительно ли разведчик существует, но занят в тот же цикл (`MoverContended`), или его нет совсем (`NoMoverExists`) и Demand не запрашивает его создание?
3. Почему повторные попытки не останавливает `CapabilityPoolExhaustionRegistry` (доказательство «пул пуст целиком»)? Проверить `ProvenPoolWideUnable` и `SettleScoutBatch` для Scout.
4. Есть ли дубль логики выбора мувера между `ReconAssignmentPlanner.HasEligibleMover`, `ScoutMoverSelector` и провижинингом (`ProvisioningManager.ScoutAssignmentFailures`)?

**Критерий готовности.** Объяснена причина по логу. Исправление либо снижает число лишних повторов без изменения решений ИИ, либо оформлено вариантом для владельца, если нужен выбор поведения.

## T2. `AirSweep` закрывается по простою

**Наблюдение.** Минимум 5 раз: строки 3777, 10578, 16542, 20415, 21263, 32161 (`Intent(AirSweep) reaped … stall 2/2, age 3–4/6`).

**Гипотеза.** Известный пробел из памяти проекта «Air recon storage gap»: AirSweep не может вылететь с авиации на хранении, строй крыльев делает только Rebase. Проверить по логам ходов перед каждым закрытием (`[ReconAirCap]`, `[Lifecycle] operation=Intent(AirSweep)`).

**Что сделать.** Подтвердить или опровергнуть гипотезу. Если подтверждена, описать минимальный путь исправления (какой владелец формирует крыло) и не расширять логику за пределы задачи.

## T3. Raid закрыт по возрасту при нулевом простое

**Наблюдение.** Строка 22053: `Intent(Raid Guard@-6,4) reaped (stall 0/2, age 10/6)`. Предупреждение по той же операции раньше, строка 20680 (`WARN … not materialised this turn`).

**Что выяснить.** Какой предел возраста (`commitmentMaxTurns` и `ShouldReap` в `MissionContinuityLayer.cs`) применяется к Raid, предназначен ли он для долгих рейдов, и связано ли закрытие с отсутствием предложения от планировщика (T4).

**Ограничение.** Порог возраста — игровой параметр. Не менять его без решения владельца; подготовить варианты и последствия.

## T4. `not materialised this turn; no planner deferral or funding bound`

**Наблюдение.** 7 раз, все для интентов уровня `Hard`: Raid Guard@-6,4 (строка 20680), ActiveDefence AirSupport Army#13 (23359), Army#38 (23850, 25729), Army#44 (33081), Raid Army#6 (24148, 25835).

**Суть.** `MissionContinuityLayer.BindFunding` предупреждает, что у живого интента нет ни предложения планировщика, ни причины отсрочки (`deferredThisPass`). По дизайну Missions должен сообщать причину, почему интент не получил исполнимого шага.

**Что сделать.** Найти, какой планировщик (Raid, ActiveDefence, AirSupport) промолчал, и добавить причину отсрочки там, где ее нет. Без изменения решений ИИ, только объяснение причины.
